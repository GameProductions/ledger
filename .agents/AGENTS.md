# Workspace Agent Rules

- **Automatic Version Bumping**: The git pre-commit hook (`scripts/prepare-commit.cjs`) automatically handles version bumping for staged commits. If you manually bump `package.json` (patch for bug fixes/refactors, minor for new features) before staging and committing, the pre-commit hook preserves your manual version without double-bumping.
- **Commit Prefixes**: The commit message must always be prefixed with the newly bumped version from `package.json` in `[vX.Y.Z]` format.

# Fleet-wide Refactoring & Engineering Standards

- **Opportunistic Abstract Refactoring**: Whenever logic or code is being added or modified, if it can be abstractly refactored to increase code quality, DRY principles, and modularity without introducing sacrifices in performance, readability, or complexity, always opt for abstract refactoring.
- **No Forced Abstractions**: Never force abstract refactoring. If abstraction does not make logical sense, introduces unnecessary layers, complicates debugging, or risks stability in a specific code block, keep the implementation concrete.
- **Rendered Text & Zero Raw JSON (Fleet-Wide Law)**: Unless the UI is explicitly and intentionally designed as a developer code editor, JSON viewer, or code block, all user-facing content — especially within activity logs, notifications, notification history, audit trails, and status inspectors — MUST ALWAYS be fully rendered into human-readable text, structured key-value attributes, and styled UI badges. Raw JSON strings, unparsed serialized blobs, or unformatted dump blocks are strictly prohibited in user-facing components.
- **User & Entity Display Name Resolution (Fleet-Wide Law)**: Whenever user accounts or entity/record types are referenced in UI components, logs, notifications, audit trails, activity chronicles, or inspectors, they MUST ALWAYS be resolved and displayed as their human-readable **Display Names** (e.g. `Jane Doe`, with their username optionally following in parentheses such as `Jane Doe (@janedoe)` instead of raw UUIDs like `01a01b9b-...` or `user_123`) and formatted **Entity Titles** (e.g. `Household Budget`, `Checking Account`, `Subscription Renewal` instead of raw database table/column identifiers like `household_budgets` or `accounts`). Raw IDs or technical snake_case keys should only appear as subtle auxiliary badges when forensically necessary.
- **Modal Centering & Background Scroll Lock (Fleet-Wide Law)**: All interactive modals, dialogs, full-history inspectors, and popups MUST be mounted at the root DOM layer (via `createPortal` to `document.body` or fixed full-viewport overlays) with **true viewport centering** (`fixed inset-0 z-50 flex items-center justify-center`). When any modal or dialog is open, background page scrolling MUST be strictly locked (`document.body.style.overflow = 'hidden'`). If the modal's contents exceed the viewable vertical space, internal scrolling MUST be handled strictly within the modal container's body (`overflow-y-auto max-h-[85vh]`) with styled custom scrollbars, preventing any outer page scrolling or unwanted backdrop shifts.
- **Overlay Stacking Context & Viewport Edge Clamping (Fleet-Wide Law)**: All temporary overlay objects (dropdown menus, pop-up panels, tooltips, flyouts, comboboxes, and floating select menus) MUST be position-aware, elevated above all static page elements (cards, sticky headers, table rows, navigation bars) via elevated z-index tiers (`z-[1000]` or higher, or mounted directly to `document.body` via `createPortal`), and strictly clamped within viewport boundaries. Temporary overlays MUST NEVER extend beyond or be clipped by the edge of the screen, card borders, or `overflow: hidden` parent containers. When rendered near a screen boundary, overlays must automatically flip axis or clamp coordinates (`max-w-[calc(100vw-24px)]`, dynamic top/bottom placement) so they remain 100% visible and unobscured.
- **Engineering Principles**: Always prioritize methods of coding that are highly efficient, secure, stable, and follow best-practices.
